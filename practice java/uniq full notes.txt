6. Thread Life Cycle:
----------------------
A thread in Java goes through several states:

|   State           |   Description                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------- |
|   NEW             | Thread object is created but  start()  not yet called.                                         |
|   RUNNABLE        | After  start()  is called; thread is ready and waiting for CPU time. (Running is part of this) |
|   RUNNING         | Thread is currently executing on CPU (conceptual state, inside RUNNABLE).                      |
|   BLOCKED         | Thread is waiting to acquire a monitor lock to enter a  synchronized  block/method.            |
|   WAITING         | Thread is waiting indefinitely for another thread action ( wait() ,  join() ).                 |
|   TIMED_WAITING   | Thread is waiting for a specific time ( sleep() ,  wait(timeout) ,  join(timeout) ).           |
|   TERMINATED      | Thread has completed execution ( run()  finished).                                             |

DeadLock:
---------
-> Deadlock is one the situation in multithreading, where two or more threads 
	are waiting for each other to release a lock.
-> A set of threads are waiting for each other in a circular chain.
		
-> how deadlock occurs ?
   -> Thread T1 locks Resource A and waits for Resource B 
   -> Thread T2 locks Resource B and waits for Resource A
      Now both threads are blocked forever this is a deadlock
	  
	How to Prevent Deadlock ?
	-> Avoid unnecessary synchronization
	-> use inter-thread-communication like wait and notify.

Design patterns:
----------------
Design patterns in Java are reusable, proven solutions to 
commonly occurring problems in software design. 
They are not specific pieces of code but rather templates or blueprints 
that help developers create flexible, maintainable, and scalable 
object-oriented applications.

1. Creational Patterns:
-----------------------
These patterns deal with object creation aiming to create objects in a manner 
suitable for the situation while hiding the instantiation logic.

Singleton:
----------
	> Ensures a class has only one instance and provides a global point of access to it.
		Problem solved:
		---------------
		You want only one object of a class to exist in entire application 
			(e.g., config, cache, logger).
Factory Method:
---------------
	> Defines an interface for creating an object, but lets subclasses 
		decide which class to instantiate.
		Problem solved:
		---------------
		> You want to create objects without exposing creation logic
			and allow subclasses/factory to decide which class to create.
		> switching one object to another is easy.
Abstract Factory:
-----------------
	> Provides an interface for creating families of related 
		or dependent objects without specifying their concrete classes.
		Problem solved:
		---------------
		You need to create families of related objects together
		without knowing their concrete classes.
Builder:
--------
	> Separates the construction of a complex object from its representation, 
		allowing the same construction process to create different representations.
		Problem solved:
		---------------
		Object has many optional parts and should be built step-by-step
		so that same process can build different versions.
Prototype:
----------
	> Creates new objects by copying an existing object (the prototype).
	Problem solved:
	---------------
	Creating an object is expensive or complex — instead of rebuilding,
	you clone an existing object.

Collection framework
---------------------
1) What is a Framework?

A framework in Java is a collection of predefined classes and interfaces that 
gives a ready-made architecture so developers don’t need to build from scratch.

2) What is Collection Framework?

The Collection Framework in Java is a set of interfaces and classes used to 
	store and process groups of objects (data).
-> Introduced in JDK 1.2
-> Present in package java.util
-> Allows storing only objects (not primitives)
-> Alternative to arrays

3) Why do we need Collection Framework? (Advantages)
| Problem with Arrays             | How Collection solves it                                  |
| ------------------------------- | --------------------------------------------------------- |
| Fixed size                      | Growable / dynamic size                                   |
| Only homogeneous allowed        | Can store homogeneous or heterogeneous (without generics) |
| No built-in data structures     | Provides ready-made structures: List, Set, Queue, Map     |
| Manual algorithm implementation | Provides inbuilt methods and algorithms                   |

4) Root Interface — Iterable

Iterable is the top-most interface of the collection hierarchy.

It provides:
Iterator<T> iterator() → to traverse elements one by one
default void forEach() → loop using lambda
Spliterator<T> → supports parallel traversal
All Collections must implement Iterable.

5) Collection - Interface (Core Methods)
Collection<E> is parent of List, Set, Queue (not Map).
| Method                              | Purpose                       |
| ----------------------------------- | ----------------------------- |
|  int size()                         | returns number of elements    |
|  boolean isEmpty()                  | checks if collection is empty |
|  boolean contains(Object o)         | checks if element exists      |
|  Iterator<E> iterator()             | returns iterator to traverse  |
|  Object[] toArray()                 | converts to array             |
|  boolean add(E e)                   | adds one element              |
|  boolean addAll(Collection c)       | adds multiple elements        |
|  boolean remove(Object o)           | removes one element           |
|  boolean removeAll(Collection c)    | removes group of elements     |
|  boolean containsAll(Collection c)  | checks for group existence    |
|  void clear()                       | removes all elements          |
|  Stream<E> stream()                 | supports stream API           |
|  parallelStream()                   | process elements parallel     |


6) When should we use Collection Framework?

Use Collection Framework when you:
-> deal with dynamic data
-> require searching, sorting, insertion, deletion
-> want to use standard data structures
-> need ready-made algorithms.

------------------

ArrayList is a resizable (dynamic) array implementation of the List interface in Java.

Ordered collection (insertion order preserved)

Allows duplicates

Allows null values

Not thread-safe (not synchronized)

Fast for read operations (get, iteration)

Slower for insert/remove in the middle

Internally ArrayList uses a dynamic array like -> Object[] elementData;

Default initial capacity = 10

When size exceeds capacity:

It creates a new array with 1.5 times

Copies old elements into new array

Example:
Old capacity = 10 → new = 15
Old capacity = 15 → new = 22

-------------------
class Node<K, V> {

    final K key;
    V value;

}

How Data is Stored:
map.put("Arun", 100);

step 1 -> find hash code for key
hash = hash("Arun");

step 2 -> find bucket index
index = hash % capacity

Step 3 -> Check bucket
If bucket empty → store new Node

If key already exists → replace value

If collision → append to linked list (or tree if list too long)

Load Factor
-----------
Definition: Load factor = ratio of number of entries to capacity.
loadFactor = size / capacity
0/16 = 0.75 -> 75%


Default load factor = 0.75

Means when 75% of buckets are filled, HashMap rehashes (resizes).

Example:

capacity = 16

load factor = 0.75
→ threshold = 16 × 0.75 = 12
So when 12th element added → HashMap resizes to 32 (doubles).

Fail fast:
----------
Iterator immediately throws an exception (ConcurrentModificationException) 
if the collection is structurally modified during iteration 
(other than via iterator’s own methods).

ArrayList, HashMap, LinkedList, HashSet, TreeMap

It checks modification count (modCount) and fails if it changes.

Faster because it directly iterates over the data.

Not thread-safe.

Modification During Iteration is not allowed.


-----------------------------------------------------------------------------

ConcurrentModificationException:
---------------------------------
ConcurrentModificationException is a runtime exception in Java 
that occurs when a collection (like ArrayList, HashMap, etc.) 
is structurally modified while iterating over it using an iterator, 
except through the iterator's own remove() method.

structural modification:
-------------------------
Adding or removing elements from the collection.
(But not just updating an existing element.)

list.add(element);   // structural modification
list.remove(element); // structural modification
list.set(1, "new");  // NOT structural modification

How it happens internally?
When you create an iterator on a collection (e.g. ArrayList), 
the iterator takes a snapshot of the collection’s internal modCount 
(modification count).

int expectedModCount = modCount;

Each time the collection is modified (add/remove), its modCount changes.

then, every time you call iterator.next(), it checks:

if (modCount != expectedModCount)
    throw new ConcurrentModificationException();

So if the collection is changed outside the iterator, the modCounts don’t match 
and you get this exception.
---------------------------------------------------------------------------------------------
Fail-Safe:
----------
Iterator does not throw an exception even if the collection is 
modified during iteration. It works on a copy of the original collection.

concurrent packages like:
ConcurrentHashMap, CopyOnWriteArrayList, CopyOnWriteArraySet

Iterator works on a separate cloned copy of the collection,
so modification in the original does not affect iteration.

Slower because it works on a copy (more memory + time).

Thread-safe (safe for concurrent access).

Modification Allowed During Iteration is allowed.
